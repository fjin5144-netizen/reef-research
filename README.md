# reef-research

REEF 策略的研究数据集 + 一页手机能看的读数。全程跑在 GitHub Actions 上，
本机关不关机都不影响。

**页面：** https://fjin5144-netizen.github.io/reef-research/

这里**只采数、只显示、不下单、不提醒、不碰持仓**。

## 这一页上没有你的钱

没有股数、没有现金、没有净值、没有实际权重——每个数字都是公开市场数据算出来的。
所以这一页可以公开挂着，不用为了藏它去买 GitHub Pro。

既省钱又真安全的做法。）

代价：手机上看不到「我该补几股」。拿目标权重乘一下，或者回本机看。

## 两条 workflow

| | 频率 | 干什么 | 提交吗 |
|---|---|---|---|
| `collect` | 收盘后 4 档 | 采数据，写 `data/` | 有变化才提交 |
| `pages` | 每小时 + 采集完 | 渲染页面，部署 Pages | **不提交** |

页面不进仓库（`docs/index.html` 在 `.gitignore` 里），由 Actions 直接部署。
不这么做的话每小时一个提交，一个月 720 个「只改了几个价格」的提交，
会把 `data/` 那些真正有意义的提交全淹掉。

公开仓库的 Actions 不限量不计费，所以这两条加起来是 **$0/月**。

## 一句话结论：为什么不是每 15 分钟跑一次

因为盘中读数**不是快照型数据**，事后能补回来：

- Yahoo 的 15 分钟 K 线可以回头拉 **60 天**
- raincheck 的 `/api/performance` 是一份 **2023-11 至今的完整 CSV**

所以收盘后取一次，和盘中戳 26 次拿到的东西一模一样。而好处是：

| | 盘中每 15 分钟轮询 | 收盘后一天一次 |
|---|---|---|
| GitHub 定时任务丢档 | 漏了 14:15 就是永久的洞 | 当天排 4 档，任一档落地即完整 |
| Actions 分钟数 | ~1270 分钟/月 | ~30 分钟/月 |
| 提交数 | 每天几十个 | 每天 1 个（无变化时 0 个） |

唯一过期不候的东西只有一样：**raincheck 首页表格里那个 signal 数字**。
`/api/performance` 里没有这一列，而首页表格只显示**当前这一轮**趋势的逐日行，
趋势一翻面旧的就查不到了。但一轮趋势能跑 28~139 天，所以一天抓一次、
偶尔漏一天也丢不了东西。

## 数据长什么样

### `data/daily.csv` —— 研究主表，一天一行

直接 `pd.read_csv` 就能用。关键列：

| 列 | 含义 |
|---|---|
| `date` | 交易日 |
| `source` | `live` = 当天实采；`reconstructed` = 事后用日线重建 |
| `qqq` `tqqq` `vix` | 当日收盘 |
| `ma50` `ma100` `ma200` `ma200_rising` | QQQ 均线及 200 日均线方向 |
| `vs_ma200_pct` | QQQ 距 200 日均线百分比（REEF 的方向条件） |
| `tqqq_rvol20` `tqqq_rvol60` | TQQQ 实际年化波动率 |
| `direction_ok` `target_weight` | **REEF 规则当日算出的目标权重** |
| `rc_*` | raincheck 黑箱信号（仅 `live` 行有） |
| `cross_agree` | 我的 200 日均线判定与 raincheck 是否一致 |

`source` 这一列要留意：`reconstructed` 行的 `rc_*` 是空的——黑箱信号没有历史接口，
只能从开始采集那天往后才有。做涉及 raincheck 的研究时记得先 `df[df.source=='live']`。

**重建行不是估算，是精确复现。** 价格派生的那些列全是价格的纯函数，事后算得出来。
已用本机 `live_ledger.csv` 里 8 个真实交易日的目标权重逐日对过，**8/8 完全一致，误差 0**。

`vix_pctile_2y` 这一列在两种来源下是**同一个口径**：严格取当日往前 504 个交易日
（point-in-time，无前视偏差）。本机 `daily_brief.py` 用的是另一个口径
（「当下拿到的全部 800 日历天」，约 549 个交易日，长度还随取数时点浮动），
那个值仍然保留在 `data/briefs/*.json` 的 `vix_pctile_2y` 里，方便和本机简报逐字对比；
主表用的是 `vix_pctile_2y_pit`。两者数值有小差异，属预期之内。

### 数据会被 Yahoo 事后修正

盘中 K 线在收盘后一两天内还会变——成交量合并、开盘价微调都很常见
（实测见过某根 15 分钟 K 线的成交量从 162 万修正到 950 万）。
每次运行都会重写最近 5 个交易日，所以仓库里存的是**修正后的版本**，这是有意的：
研究要的是结算完的数据，不是第一眼看到的数据。代价是同一天的前几档 cron 会各产生
一个提交，那不是噪音，是数据真的变了。

### `data/intraday/<日期>.csv` —— 15 分钟 K 线

QQQ / TQQQ / VIX，**含盘前盘后**（04:00–20:00 ET，约 64 根/天）。
事后想只看常规时段随时能过滤掉，但当时没存下来就补不回来了——Yahoo 只给 60 天。

### `data/briefs/<日期>.json` —— 当日完整读数

`daily.csv` 的超集。主表里没有的东西（离线提醒价位、趋势长度历史分位、
分档止盈线、当日的告警文本）都在这里。

### `data/raincheck/<日期>.json` —— 黑箱信号快照

上面说的那个过期不候的东西，单独存一份，免得将来改 brief 结构时把它一起弄丢。

## 怎么跑

平时不用管，Actions 自己跑。手动的话：

```bash
python3 collect.py
```

拉满 60 天盘中历史 + 用日线重建十年主表（建仓库时跑过一次，一般不用再跑）：

```bash
python3 collect.py --backfill
```

纯标准库，没有 `requirements.txt`，不需要装任何东西。

## 会怎么坏

**最可能的一种：Yahoo 开始限流 GitHub 的机房 IP。** 家里宽带没事不代表机房没事。
`brief.py` 里已经做了 6 次重试 + `query1`/`query2` 双主机轮换，但挡不住真被封。
真发生了你会收到 GitHub 的失败邮件——workflow 最后一步 `--check` 专门干这个：
主表最新一行超过 4 天没更新就把 job 标红。

**第二种：raincheck 改接口。** 那边是抓 Google Sheets 导出的 HTML 表格，
不是正经 API，随时可能变。`brief.py` 对这种情况是软失败：raincheck 那部分留空、
记一条 warning，价格派生的读数照常产出。所以 `rc_*` 列突然连续变空 = 该去看一眼了。

**自愈**：每次正常运行都会顺手重写最近 5 个交易日的盘中文件。连续四天 cron 全丢，
第五天成功那次会把前面全补回来，不用人工干预。
